# Live approval status

mayi-approve status is a noninteractive approver-role aggregate snapshot directly from the existing approval socket, never Journald or LIST_PENDING reconstruction. No PAM/session/view or consume request is made. Scope matches the existing approver's global LIST_PENDING visibility, but returns counts only (no commands, UID lists, tokens or private request IDs). Console health is not tracked and is not claimed.

QUEUE_STATUS validates the existing kernel SO_PEERCRED/NSS approver role, strict protocol/type-only message and absence of descriptors. It returns before ordinary authority handling, expiry/session cleanup or denied-peer session revocation. Snapshot is computed with one broker lock and one monotonic expiry sample; serialization/framed write occurs after unlocking. O(128 retained requests + dependency edges); ephemeral synchronous execution observations are additionally bounded by the eight existing request workers. No queue cleanup, approval mutation, view creation or auth-session renewal. Existing auth quotas/retention are unchanged.

Important architecture discovery: QueueState::Running previously meant claimed dispatch, not OS child spawn. Pending/ready/dispatch fields alone cannot truthfully answer actual running. The minimal opt-in EXEC_REQUEST_OBSERVE variant uses the same root-authenticated execution socket/body/claim semantics; root sends one correlated EXEC_STARTED frame only after successful Command.spawn. One nonblocking send, no retry, no waiting for acknowledgement and no execution authority effect. Final EXEC_RESPONSE remains mandatory and the original 300-second transaction deadline does not reset. Legacy EXEC_REQUEST is unchanged. No new root socket/general-purpose query endpoint. Lost/malformed observation can remain dispatching or yield the existing unknown outcome, never trigger replay/fallback.

Queued phase metadata remains on the existing Request. Synchronous in-flight observations use a private <=8-entry map because normal consumed-request retention can remove an executing synchronous record before the IPC finishes; extending authorization retention just for statistics would be wrong. It cannot restore/consume a request and is removed when that call returns. Counts include retained requests plus these current calls exactly once. Worst-case active bound is 136; no unbounded correlation cache.

Running means broker observed an actual spawn and has not yet observed the final RPC outcome. Dispatching means execution was claimed but spawn remains unconfirmed (including root's serial executor backlog). Unknown outcome is not proof that a child stopped; queued terminal unknown outcomes are reported separately outside active total. Physical process-tree supervision, durable active-state recovery, execution-start TTL and general exactly-once effects are not claimed.

Options: status, --json, --watch, --interval 0.5..60 seconds (watch only, default1). See STATUS_PROTOCOL/JSON_SCHEMA/WATCH_MODE and QUEUE_STATE_MAPPING. No privilege changes or host installation are part of development qualification.
